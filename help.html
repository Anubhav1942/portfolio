Help & Setup Guide

How the platform works, how to connect a domain, and how to lock it down properly.

How it works

Every portfolio on this platform is powered by the same set of HTML template files, hosted on Firebase Hosting. The content -- your name, bio, work, case studies -- lives in Firestore, not in the HTML. When a visitor loads any page, the JavaScript reads the hostname from the browser URL, looks that up in a Firestore domains collection to find your user ID, then fetches your specific content and renders it.

This means the template files are shared across all users. You do not get a separate codebase or repo. What you get is your own isolated content document in Firestore and a custom domain that routes to it.

Visitor arrives at yourname.com → Firebase Hosting serves the HTML template
Template JS runs → reads window.location.hostname = "yourname.com"
Firestore lookup → domains/yourname.com → finds your uid
Content fetch → users/{uid}/portfolio/content → your data
Page renders with your content

Your admin panel at /admin.html uses Firebase Auth to verify your identity, then reads and writes only your content document. No user can read or write another user's content -- this is enforced by Firestore security rules on the server side.

New user flow

Here is the full sequence from signing up to having a live portfolio at your own domain.

1

Create an account

Go to the platform page and click "Create your portfolio". Sign up with your email. You will receive a verification email -- click the link in it before trying to log in. Unverified accounts cannot access the admin panel.

2

Fill in your content

After signing in you are taken to the admin panel. Work through each section: Home (hero, projects, experience), About (bio, sidebar), and Profile & Links (your name, tagline, contact details). Everything saves automatically as you type -- there is no publish or save button to click.

3

Buy a domain

Purchase a domain from any registrar -- GoDaddy, Namecheap, Cloudflare, Porkbun, wherever you prefer. The registrar does not matter; you just need the ability to edit the domain's DNS records. A .com, .in, .io, .co -- any extension works.

4

Connect the domain in Firebase Console

Go to the Firebase Hosting Console, click "Add custom domain", and type your domain. Firebase will give you DNS records to add. Add them in your registrar's DNS settings. Firebase will verify ownership and issue an SSL certificate automatically. This step is covered in detail below.

5

Register the domain in your admin panel

In your admin panel, go to Settings → Domain & Analytics. Type your domain (e.g. yourname.com) and click "Register domain". This creates the Firestore mapping so visitors arriving at your domain get your content, not someone else's.

6

Your site is live

Once DNS has propagated (usually within an hour, sometimes a few hours), yourname.com will show your portfolio. Any future edits in the admin panel go live immediately -- no re-deploy needed.

Connecting a custom domain

The domain connection requires two things to happen: Firebase must verify you own the domain, and your DNS must point the domain to Firebase's servers. Firebase walks you through this in the Console with specific records to add.

The records Firebase will give you look like this (exact IPs will be shown in the Console):

TypeName / HostValuePurpose
A@199.36.158.100Points root domain to Firebase
TXT@hosting-site=portfolio2anubhavpProves you own the domain
CNAMEwwwyourname.comwww subdomain (optional)
⚠ If your domain previously pointed to GitHub Pages, you will have old A records (185.199.x.x) that need to be deleted first. Firebase's ACME challenge will fail as long as those old records exist, because the domain is still answering from GitHub's servers.

After adding the records, return to the Firebase Console dialog and click Verify. The TXT record verifies almost instantly. The A record may show a clock icon (pending) for 10-60 minutes while DNS propagates globally -- this is normal. Once both show green checkmarks, Firebase issues the SSL certificate and your domain is live over HTTPS.

ℹ DNS propagation time depends on the TTL set on your old records. Records with a 1-hour TTL can take up to an hour to fully replace globally. Records with 600-second (10 minute) TTLs switch faster. You can check current DNS state at dnschecker.org.

Firebase Console steps

These are the one-time Console actions required to fully set up the platform. They cannot be done from code -- they must be done manually in the Firebase web interface.

1

Enable Email/Password authentication one-time

Go to Authentication → Sign-in method. Enable "Email/Password". Also enable "Email link (passwordless sign-in)" if you want to add that later. Without this enabled, no one can create an account.

2

Apply Firestore security rules one-time

Go to Firestore Database → Rules. Replace the default rules with the ones in the section below. Click Publish. Without this, any authenticated user can read or write any other user's content.

3

Apply Storage security rules one-time

Go to Storage → Rules. Replace the default rules with the Storage rules in the section below. Without this, uploaded images are either fully public or fully locked -- neither is correct.

4

Add custom domains for each user per user

Each time a user wants to connect their domain, go to Hosting → Add custom domain and type their domain. Firebase will generate DNS records for them to add. You can delegate this step to users if you give them access to the Firebase project, or handle it yourself for each new user.

⚠ Step 4 (adding custom domains for each user) is currently a manual process requiring Console access. Each user's domain must be individually added in Firebase Hosting before their DNS changes will work. This is a Firebase platform limitation -- there is no API to add hosting domains from client-side code.

Firestore security rules

Paste the following into Firestore Database → Rules and click Publish. These rules enforce that each user can only read and write their own content, while allowing public read access to the domain mapping and legacy content path that portfolio pages need to load.

rules_version = '2'; service cloud.firestore { match /databases/{database}/documents { // Each user's portfolio — only they can read or write it match /users/{uid}/portfolio/content { allow read, write: if request.auth != null && request.auth.uid == uid; } // Domain-to-uid mapping — public read (needed to load any portfolio), // only the domain owner can write it match /domains/{domain} { allow read: if true; allow write: if request.auth != null && request.auth.uid == resource.data.uid; allow create: if request.auth != null && request.auth.uid == request.resource.data.uid; } // Legacy shared path — public read for backward compat, // authenticated write only (tighten once migration is complete) match /portfolio/content { allow read: if true; allow write: if request.auth != null; } } }

Once multiple users are fully migrated to domain-based routing and no public pages fall back to the legacy portfolio/content path, the last rule can be changed to allow write: if false to fully lock it down.

Firebase Storage security rules

Paste the following into Storage → Rules and click Publish. These rules allow each user to upload to their own image folder and allow anyone to read images (since portfolio images must be publicly accessible). Maximum file size is enforced at 10 MB.

rules_version = '2'; service firebase.storage { match /b/{bucket}/o { // User image uploads — public read, write only by the owner match /users/{uid}/images/{allPaths=**} { allow read: if true; allow write: if request.auth != null && request.auth.uid == uid && request.resource.size < 10 * 1024 * 1024 && request.resource.contentType.matches('image/.*'); allow delete: if request.auth != null && request.auth.uid == uid; } // Everything else is denied by default } }
ℹ The request.resource.contentType.matches('image/.*') check prevents users from uploading non-image files (PDFs, scripts, etc.) disguised as images. The 10 MB cap avoids Storage quota abuse.

Troubleshooting

Domain verification keeps failing with ACME 404 errors. The old A records from your previous host (e.g. GitHub Pages) are still active in your DNS. Go back to your registrar, delete any A records you did not add yourself, then click Verify again. Use dnschecker.org to confirm the A record is resolving to Firebase's IP before retrying.

Portfolio shows blank content after domain connection. The domain was not registered in the admin panel. Go to Settings → Domain & Analytics, type your exact domain (no https://, no trailing slash), and click Register domain. The Firestore mapping must exist before the public page can find your content.

Uploaded image shows a broken link. Firebase Storage rules may not have been applied yet. Go to Storage → Rules in the Firebase Console and paste the Storage rules above. Also confirm the file type is an image (jpg, png, webp) and is under 10 MB.

Admin panel redirects to login even though I am signed in. Email verification is required. Check your inbox for the verification email sent at signup and click the link. If it expired, go to the login page and click "Resend verification email".

Content edited in admin panel is not showing on the public site. The public pages load content from Firestore on every page load -- there is no cache to clear. If changes are not appearing, open browser DevTools (F12) and check the Console for Firestore errors. The most common cause is security rules not yet applied, or the domain not registered in Firestore.
